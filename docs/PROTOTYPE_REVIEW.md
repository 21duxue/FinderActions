# FinderActions 原型 Review

## 结论

当前原型已经能回答三个核心设计问题：

1. Finder 右键菜单应该折叠到 `FinderActions ▸` 子菜单，还是直接平铺？
2. `New File Here` 应该弹出输入框，还是直接创建默认文件？
3. 设置窗口应该做到多简？

但当前版本仍然偏“正常路径演示”，缺少失败路径、权限路径和真实系统边界。它适合用来做交互方向确认，不足以直接指导最终实现。

## 1. 已验证的优点

### 1.1 三个设计方向可切换

原型提供三个方向：

1. **Native Minimal**
2. **Compact Utility**
3. **Power User**

每个方向都会同步调整：

- 菜单层级
- New File Here 的交互
- 设置窗口密度

这使原型可以用来比较设计取向，而不是只看静态截图。

### 1.2 三个核心动作都可交互

原型支持：

- `New File Here…`
- `Open Terminal Here`
- `Copy Path Here`

三个动作都能真实触发对应的界面状态：

- 弹出文件名输入框
- 直接创建文件
- 打开模拟终端
- 显示复制成功反馈

### 1.3 设置密度差异清楚

三个方向下的设置窗口有明显差异：

- Native Minimal：只保留核心开关、终端选择和默认文件名
- Compact Utility：更紧凑，适合小窗口
- Power User：增加更多可用但不一定属于 v1 的控制项

这能帮助判断 v1 应该停在哪个复杂度上。

## 2. 明确问题

### 2.1 失败路径展示不足

当前原型主要展示正常流程，缺少：

- 文件名非法
- 目录无权限
- Finder 扩展未启用
- 终端未安装
- 目标位置不可写
- File Provider 目录不支持

这些是调研中反复出现的真实问题。原型目前只处理了“空文件名”和“包含 `/`”两种简单错误。

### 2.2 设置窗口仍是模拟，不代表最终 AppKit 行为

原型中的设置窗口是 HTML/CSS 模拟，不代表真实 AppKit 的：

- 系统控件尺寸
- 键盘导航
- 系统扩展设置跳转
- 原生开关和下拉框行为

因此它只能用来判断信息架构和层级，不能用来评估最终视觉还原度。

### 2.3 菜单层级判断仍偏主观

原型展示了两种菜单形态：

- 子菜单
- 平铺

但从当前原型本身还不能证明哪种更符合用户实际使用频率。这个判断目前主要来自：

- 参考项目的功能密度
- v1 只保留三个动作的定位
- 避免污染 Finder 顶级菜单的目标

这属于**工程判断**，不是用户测试结论。

### 2.4 终端选择未显示选中状态

原型中的 `Open Terminal Here` 会打开模拟终端，但模拟终端没有显示当前选择的终端名称，也没有区分：

- Apple Terminal
- iTerm2
- Ghostty
- Warp

用户无法从交互反馈里确认“我选择的终端是否生效”。

### 2.5 文件名输入框的键盘行为不完整

目前支持：

- Enter 创建
- Escape 取消

但仍有不足：

- 未实现完整焦点捕获
- 取消后焦点不会返回 Finder 画布
- 错误提示不区分输入框焦点和全局提示
- 没有展示非法文件名的完整列表

### 2.6 右键菜单位置可能溢出屏幕

当前右键菜单位置直接使用鼠标坐标，没有做边界处理。在小窗口或靠近屏幕边缘时，菜单可能被裁切。

### 2.7 File Provider 场景未显式表达

调研已确认 iCloud Drive、OneDrive、Dropbox、Google Drive 等 File Provider 目录存在兼容性问题。当前原型没有说明这一限制，也没有提供对应提示。

### 2.8 三个设计方向的功能差异还不够鲜明

当前差异主要体现在设置密度上，但：

- Native Minimal 和 Power User 的菜单行为几乎一致
- Compact Utility 与 Native Minimal 的差异主要来自开关数量
- 三个方向缺少“为什么选这个方向”的显式说明

## 3. 风险

### 3.1 过度承诺

原型中显示了 “Local folders, external drives, and SMB shares are supported.” 但真实实现中还需要验证：

- 外接盘挂载/卸载
- SMB 权限
- Finder 侧边栏图标替换
- 系统版本差异

原型不应暗示这些能力已经完全解决。

### 3.2 设置复杂度失控

Power User 方向展示了更多控制项，包括：

- 显示子菜单
- 显示图标
- 复制多路径

这些能力不属于 v1。如果保留在原型中而不明确标注为“演示”，容易导致需求膨胀。

### 3.3 视觉还原风险

原型使用 Web 技术模拟 macOS 视觉，真实 AppKit 控件的行为、字体、间距和层级会有差异。不能把 HTML 原型当成最终视觉规格。

### 3.4 权限流程被简化

Finder 扩展启用、系统设置跳转、权限拒绝等流程目前没有完整展示。这是实现阶段的主要风险之一。

## 4. 改进建议

### 4.1 增加错误状态

应补充至少四类交互反馈：

1. 文件名非法
2. 已存在同名文件
3. 目标目录不可写
4. Finder 扩展未启用

这能让原型覆盖主要失败路径。

### 4.2 限制 Power User 范围

Power User 方向应明确标注为“超出 v1 的演示”，或删除不属于 v1 的选项，避免把原型误读为需求范围。

### 4.3 显示当前终端

模拟终端应显示当前选择的终端名称，并随设置变化更新。

### 4.4 完善键盘行为

应实现：

- 文件名输入框打开时自动聚焦
- Enter 创建
- Escape 取消
- 取消后焦点返回 Finder 画布
- 关闭菜单后焦点不丢失

### 4.5 菜单边界处理

右键菜单应根据视口自动调整位置，避免溢出。

### 4.6 增加限制说明

在原型中明确展示：

- 本地目录、外接盘、SMB 目标
- File Provider 目录不支持或可能不可用

### 4.7 添加“当前方向”说明

每个方向应包含一句明确说明，解释它适合的用户和取舍，例如：

- Native Minimal：适合绝大多数用户
- Compact Utility：适合偏好更快操作的用户
- Power User：适合需要更多控制但接受复杂设置的用户

## 5. 推荐决策

基于当前原型，建议采用：

1. **默认使用 `FinderActions ▸` 子菜单**
2. **`New File Here` 默认弹出输入框**
3. **设置窗口采用 Native Minimal**
4. **v1 不提供平铺菜单开关**
5. **v1 不实现 Power User 中的额外选项**
6. **Power User 方向仅用于对比，不作为 v1 需求**

## 6. 后续动作

在进入原生实现前，应先完成：

1. 修改原型，补充失败路径和边界说明
2. 明确三个方向的定位说明
3. 显示当前终端名称
4. 处理菜单位置溢出
5. 完善键盘操作和焦点管理
6. 再次人工检查原型是否仍然保持单文件、无依赖、可直接双击打开

## 7. Review 后已完成的修改

根据上述结论，原型已完成以下修改：

1. 增加了失败状态模拟：
   - 正常
   - 只读目录
   - Finder 扩展未启用
   - 终端未安装
2. 增加了 v1 范围提醒，明确哪些功能属于 v1，哪些不属于 v1
3. 设置窗口现在显示：
   - Finder 扩展状态
   - File Provider 目录可能不可用的提示
   - 当前默认终端
4. New File Here 输入框增加了：
   - 空文件名错误
   - 含 `/` 的文件名错误
   - `.` / `..` 保留名错误
   - 只读目录错误
   - Finder 扩展未启用错误
5. 增加了键盘焦点管理：
   - 输入框打开后自动聚焦
   - Enter 创建
   - Escape 取消
   - 取消后焦点返回来源控件
   - 输入框内 Tab 循环
6. 右键菜单会根据视口自动调整位置，避免被裁切
7. 模拟终端会显示当前选择的终端名称

这些修改仍保持原型为单文件 HTML，不引入任何外部依赖。

## 8. 二次 Review：去模板化与双语要求

### 8.1 本次结论

原型已按以下要求重做：

- 默认中文
- 支持中文 / English 切换
- 去掉厚重的深色渐变、玻璃拟态和大阴影
- 圆角控制在 10px 以内
- 以边框、留白和真实文本密度分层
- 不使用 emoji 作为图标
- 不使用营销化空话
- 恢复“真实产品信息”的表达方式：
  - 说明本地磁盘、外接磁盘、SMB 的支持范围
  - 说明 iCloud Drive、OneDrive 等 File Provider 目录的限制
  - 保留权限失败和终端缺失状态
  - 保留设置窗口中的扩展启用状态
  - 保留错误信息中的具体原因

### 8.2 当前优点

1. **默认中文**
   - 页面标题、菜单、设置、提示和错误信息默认使用中文
   - 用户可切换 English
   - 切换不改变交互流程

2. **信息密度更接近真实产品**
   - 设置窗口不只是三个开关
   - 包含默认终端、默认文件名、扩展状态和 File Provider 限制
   - 菜单和设置不会用大段宣传文案代替具体操作

3. **视觉噪音降低**
   - 使用浅色系统字体界面
   - 以边框和留白分层
   - 去掉发光阴影和大面积渐变
   - 主色只保留一个，用于选择和主要按钮

4. **边界状态更完整**
   - 支持“正常 / 只读 / 扩展关闭 / 终端缺失”模拟
   - 错误信息具体、可理解
   - 设置窗口会显示扩展启用状态

### 8.3 仍然存在的问题

1. **原型仍不能代表 AppKit 视觉**
   - HTML 的按钮、下拉框、开关和字体度量与 macOS 原生控件不完全一致
   - 原型只能用于信息架构和交互验证，不能用于像素级验收

2. **双语切换仍偏“一次性切换”**
   - 当前只切换主要界面文案
   - 还没有测试完整双语文案在长文本、错误信息和设置窗口中的长度差异
   - 英文文案可能比中文更长，部分布局在小窗口下可能需要进一步调整

3. **Power User 方向仍有需求膨胀风险**
   - 原型中的“高级用户”方向包含更多控制项
   - 这些控制项必须明确视为对比方向，不应默认进入 v1

4. **浏览器行为与 Finder 行为不同**
   - 右键菜单位置和键盘行为只是模拟
   - FinderSync 提供的菜单事件、选中项和系统菜单样式仍需在原生实现中验证

5. **File Provider 限制仍需原生验证**
   - 原型只能说明限制
   - 不能证明真实 Finder 中一定不显示菜单

### 8.4 推荐保持的设计决策

1. 默认中文
2. 支持中文 / English 切换
3. 默认 `FinderActions ▸` 子菜单
4. `New File Here` 默认弹出输入框
5. 设置窗口采用“原生简洁”方向
6. v1 不引入平铺菜单开关
7. v1 不实现 Power User 中的额外控制项

### 8.5 下一步验证

在开始原生实现前，建议完成：

1. 在浏览器中人工检查中文和 English 两种状态
2. 测试窄屏布局
3. 检查键盘焦点和 Escape / Enter 行为
4. 确认错误信息在中英文下都清楚、具体
5. 确认原型仍为单文件、无依赖、可直接双击打开

## 9. 第三次 Review：视觉与信息层级重做

### 9.1 本轮修改

原型已按 `ui-ux-pro-max` 的检索结果重新设计，但未直接采用搜索返回的紫色 AI 风格，因为该风格与 macOS Finder 工具的产品类型不匹配。实际采用的方向来自更合适的检索结果：

- `minimalism-and-swiss-style`
  - 干净、留白、功能优先、高对比、网格布局
  - 避免不必要阴影和渐变
- 无障碍 / 键盘交互检索结果
  - 所有可操作控件必须有可见焦点
  - 模态框内焦点必须可循环
  - 控件状态必须暴露给辅助技术
- 表单反馈检索结果
  - 校验信息应靠近字段
  - 提交失败后焦点应指向错误
- 中性色盘检索结果
  - 以黑白灰为基底，用一个暖色 accent

### 9.2 新视觉方向

当前原型采用：

- 浅色背景 `#f6f6f7`
- 白色面板
- 灰色边框
- 深灰文本
- 一个主色：`#a16207`
- 三个状态色：
  - 成功 `#15803d`
  - 警告 `#b45309`
  - 错误 `#b91c1c`
- 圆角最大 `10px`
- 阴影只保留极轻的产品表面层次
- 系统字体栈
- 不使用 emoji 图标
- 不使用渐变
- 不使用玻璃拟态

### 9.3 信息结构

左侧用于决策，右侧用于结果：

- 左侧：
  - 设计方向
  - 三个核心设计问题
  - 边界状态模拟
- 右侧：
  - Finder 窗口模拟
  - 设置窗口模拟

这个结构的目的不是展示“卖点”，而是让每个控制项直接影响右侧交互，方便对比。

### 9.4 仍存在的问题

1. 原型仍是 HTML，不是 AppKit。
   - 原生实现时按钮、开关、下拉框、菜单样式会由 macOS 提供。
   - 原型只能用于决策，不能用于像素级还原。

2. 当前只做了浅色模式。
   - 如果产品后续需要深色模式，需要单独设计令牌，不应直接反色。

3. 原型没有覆盖全部文件名边界。
   - 当前覆盖空文件名、`/`、`.`、`..`、重名追加。
   - 文件名过长、名称以点结尾、大小写冲突等仍需在核心模块中测试。

4. File Provider 限制只是提示。
   - 原型不能验证真实 Finder 是否显示菜单。
   - 该限制必须在原生实现中单独测试。

5. 英文文案较中文更长。
   - 小窗口下需要人工检查是否溢出。
   - 目前只做了基础响应式，没有做完整双语排版测试。

### 9.5 本轮结论

当前版本比上一版更符合 macOS 工具类产品：

- 视觉更接近原生桌面工具
- 信息层级更清楚
- 操作路径更短
- 状态更完整
- 装饰更少
- 每个面板的存在理由更明确

仍然推荐：

- 默认中文
- 支持中文 / English
- 默认 `FinderActions ▸` 子菜单
- `New File Here` 默认弹出输入框
- 设置窗口采用原生简洁方向

## 11. 第五次 Review：功能范围收敛

本次调整后的 v1 动作为：

1. New File Here…
2. Open Terminal Here
3. Copy Path Here
4. Copy Name Here

已明确移除：

- New Folder Here
- Copy Shell Path Here

移除理由：

- `New Folder Here` 与 macOS Finder 原生能力重复

调整后：

- 菜单从 6 项收敛为 4 项
- 设置窗口只保留 4 个动作开关
- 原型不再模拟文件夹创建
- 原型不再模拟 Shell 路径复制
- `Copy Name Here` 保留，用于复制选中项名称

仍然存在的问题：

- `Copy Name Here` 的多选行为需要在原生实现中验证
- 无选中项时复制当前目录名的行为需要在真实 Finder 中验证
- 子菜单和平铺两种结构在 Finder 中的实际层级仍需原生验证
